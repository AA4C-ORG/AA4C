# 0016 远程接收必须安装；近场可免安装直传

状态：已接受（2026-10-30）

现有文档同时承诺了三件不能直接共存的事：远方的人不装 AA4C 也能点分享链接取文件；aa4c.com 只有静态页面；
项目没有公共中转、存储或信令服务。静态落地页本身无法把浏览器连接到 NAT 后的发送设备，也不能替发送方保存文件。

决定：v1 按“远程”和“人在现场”划清产品边界。

- **远程接收必须安装 AA4C**：联系人发送和一次性发送链接都由两端 AA4C 完成；链接只携带一次性凭证、候选地址与中转提示，
  实际传输仍走连接阶梯。
- **近场安装可选**：人在现场时，优先让用户在“用 AA4C 接收”和“无需安装”之间选择。有可互访的本地 IP 链路时，
  “无需安装”使用扫码收发页；操作系统确实提供蓝牙、红外或系统附近分享时，可以通过平台直传适配器交给系统完成。
- **无线方式是能力，不是承诺**：同一局域网、Wi-Fi Direct、临时热点负责建立本地 IP 链路；蓝牙、红外和厂商附近分享只有在当前
  两端平台真正支持时才显示。AA4C 不把它们伪装成一个所有平台都具备的跨平台协议。

aa4c.com 的 `/s/#…` 只负责把一次性发送链接交给已安装的 App；没有安装时显示下载指引，不代理、不存储文件。
因此 v1 不把“远程浏览器下载”写进完成标准。

近场各路径的选择、信任边界与降级顺序见[近场交付](../../book/src/network/proximity.md)。其中用 AA4C 直连时仍有设备认证与端到端加密；
扫码网页受局域网明文 HTTP 的已知限制；平台直传则使用操作系统自己的确认与安全语义，不能显示为“AA4C 加密直连”。

未来若要支持，必须另写 ADR，完整回答浏览器端加密、可信 HTTPS、NAT 后可达性、发送方离线、超大文件流式传输与谁来运行网关。
可研究“自建中转站 + 静态页面中的小型加密客户端”，但不能把它悄悄变成官方服务。
