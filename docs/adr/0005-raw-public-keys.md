# 0005 原始公钥代替 X.509

状态：已接受；macOS 实测通过，Linux/Windows 待 CI 确认（2026-10-30）

第一代为了让 TLS 认得设备，给每台设备生成自签 X.509 证书，再从证书里取指纹做固定，为此引入 rcgen、x509-parser 两套证书依赖。
我们的身份本来就是一把 Ed25519 公钥，X.509 是绕了一圈。

决定（待实验）：QUIC 握手用 TLS 1.3 的**原始公钥**（RFC 7250，rustls 0.23 起支持），双方直接出示 Ed25519 公钥，
校验它与已认证的信标连接卡片、二维码、链接或已知设备证书中的预期公钥一致，再在第一条控制消息里出示设备证书链
（个人密钥签名）。拨号方永远不能先接受任意服务端公钥。监听方只在两种情况下接受未知来电公钥：本地 IP 链路上的
「所有人」模式，或本机有未过期的邀请口令 / 一次性发送口令；在 Hello 验证完成前把它限制为 Stranger，凭口令进来的连接
只允许出示口令。

## 实验结果

`experiments/raw-quic`（quinn 0.11 + rustls 0.23，ring provider，TLS 1.3 only，ALPN `aa4c/1`）在本机回环上证明了：

- 两端用 Ed25519 原始公钥完成双向认证握手，并能在流上收发数据；握手后用 `Connection::peer_identity()` 取回对端经认证的公钥。
- 拨号方给出预期服务端公钥，不符则握手失败；监听方给出预期来电公钥，不符的客户端拿不到任何数据（TLS 1.3 下客户端先看到握手成功，再收到关闭，
  所以判据是“对端从未被当作已认证”）。
- 监听方可选“接受任意有效公钥”，仍能在握手后取到对端公钥并按 Stranger 处理——这是“所有人”模式与口令来电的实现基础。
- SPKI 解析只认固定 12 字节前缀 + 32 字节的 Ed25519，其他算法与畸形编码一律拒绝。
- 不需要 rcgen、x509-parser：整个传输栈（quinn、rustls、ring、tokio）共 37 个唯一 crate，远低于 `aa4c` 130 的预算。

**crypto provider**：实验用 ring（含 C 与汇编，进入依赖清单）。aws-lc-rs 与纯 Rust provider 没有实测；Android/iOS 交叉编译与
Linux/Windows 结果出来之前，provider 仍是暂定，不写成最终结论。拨号方的“握手时必须验证”由 `Expect::Exactly` 强制，`Expect::Any` 只给监听方。

**还没证明的**：跨网络（NAT、中转站）下的行为；真实设备证书链在 Hello 里的验证；Android/iOS 构建。这些属于后续里程碑，不影响本 ADR 的决定。
