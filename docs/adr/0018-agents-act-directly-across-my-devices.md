# 0018 Agent 在我的设备之间直接动手

状态：已接受（2026-10-30）。设计见 [book/src/surfaces/agents.md](../../book/src/surfaces/agents.md)。

AA4C 要对 AI agent 友好：agent 应该能经 AA4C 在我的设备之间传文件、查看和操作我的其他设备。
原设计里 MCP 默认没有任何发送目标，用户必须先用 `--allow-to` 逐个授予，连「把这份报告发到我手机上」都要先配置；
跨设备操作（例如在 NAS 上查空间）也没有落到协议上。

决定：「我的设备」之间，agent 不需要额外授权就能直接动手；越出「我」的边界，仍然要人显式授予。

- **发给我的设备**：MCP 会话默认可以把文件发给任何一台未被吊销的「我的设备」，不用逐个授予；仍受 `--read-root` 与字节预算约束。
  发给联系人仍要 `--allow-to`，创建一次性发送链接仍要 `--allow-share`，陌生人永远不行。用户可以用 `--no-my-devices` 关掉这项默认。
- **在我的设备上操作**：agent 可以经 AA4C 在我的另一台设备上调用 `read` 与 `act` 命令（例如在 NAS 上查空间、让 NAS 把文件发到手机）。
  目标设备按自己的规则重新生成 `CallerContext`：级别最高到 `act`；涉及路径的命令只能碰那台设备的「收到的」与它共享出来的目录。
  每台设备都可以关掉「接受我其他设备上 agent 的调用」。
- **信任不变**：加入设备、添加联系人、开放远程访问的服务等 `trust` 级操作仍只能由人完成（ADR 0011）；跨设备调用永远进不了 `trust`。

理由：我的设备之间本来就是零确认互传，文件发到自己的另一台设备并没有离开「我」。提示注入在这条路径上最坏只能把获准目录里的文件
挪到我另一台设备上；真正的外泄出口（联系人、一次性链接、陌生人）仍要人事先授予。

后果：任何一台我的设备失守，攻击者都能借它驱动我其他设备上的 `read` 与 `act`；这与个人私钥在每台设备上的风险同源（ADR 0002），
吊销那台设备即可切断。端口转发仍要 `--allow-tunnel`，因为它给出的是网络访问，不只是文件。
