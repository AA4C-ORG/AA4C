# 0006 redb + config.toml 代替 SQLite

状态：已接受，附 M0 验证条件（2026-10-30）

第一代用 rusqlite 的 bundled 模式，等于把 SQLite 的 C 源码编进每个构建；数据库文件对人和 agent 都不透明，13 个迁移脚本
还藏过「重建表时顺着外键级联删光子表」这种会波及全部老用户的 bug。

决定：**状态**（设备、联系人、空间、索引、传输记录、分享）放 redb（纯 Rust、ACID 的嵌入式键值库）；
**配置**放数据目录下的 `config.toml`，人和 agent 都能直接读改，引擎启动时校验。数据格式版本记在 redb 的元数据表里，
升级逻辑在 Rust 里写并配测试。

考虑过的方案：继续用 SQLite（成熟、能写 SQL 排查）——但违背「尽量只用 Rust」；排查需求由 `aa4c` 的只读命令满足。

**为什么不是 fjall**：fjall 是 LSM 存储，擅长持续写入和超大数据集，代价是后台压缩带来的 I/O 波动、memtable 与 block cache 的调参，
并且默认只刷到操作系统缓存，掉电安全要显式 `SyncAll`；身份、吊销、信任策略忘记一次就是事故。AA4C 的核心状态量小而要求强一致，
引擎本来就是单写者，redb 的单写事务、默认强持久化、单文件、无后台线程正好匹配。fjall 保留为将来 `folder_index`（可重建、写密集）
超出 redb 能力时的候选，到时只迁这一张表，核心状态不动。

**M0 验证条件**（不满足则回到本 ADR 重议）：

- `folder_index` 灌入 100 万条后的导入、查询、更新、删除耗时与内存；
- 写事务中强杀进程后的恢复，含 quick-repair 的提交开销；
- 大量删除后的文件膨胀与 `compact()` 耗时；
- 升级前备份与恢复；
- 键值编码带显式 schema 版本，不依赖 Rust 结构体布局；
- 身份、联系人、吊销、策略、空间成员的写事务均为强持久化；地址缓存等可重建数据才允许弱持久化。

存储接口按业务操作（如 `accept_contact`）设计，不暴露通用的 `put(table, key, bytes)`，这样日后换后端不会波及业务代码，
也不会退化成再造一套数据库 API。
