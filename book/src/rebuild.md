# 第二代重建方案

第二代不是在第一代上继续删依赖，而是在 `AA4C-ORG/AA4C` 建立新的产品模型、协议和代码库。
第一代只作为行为证据与事故档案，不作为脚手架。决定见
[ADR 0014](../../docs/adr/0014-clean-break-from-v1.md)。

## 为什么不能原地瘦身

第一代已经验证了局域网发现、加密传输、续传、打洞和自建中转，但它的结构同时背着两套产品：
设备连接与传输，以及下载器、BT、本地 AI、知识库。当前基线是：

- `Cargo.lock` 里 648 个包；仅正常运行时的工作区依赖去重后约 487 个；
- `node_modules` 约 185 MB；
- Rust、TypeScript/Vue、Kotlin，以及 aria2、Transmission、llama-server 等外部程序；
- 约 4 万行 Rust / TypeScript / Vue / Kotlin 产品代码；
- 13 个 SQLite 迁移和多条重叠的网络路径。

在这个结构上逐项删除，会同时保留旧身份模型、旧协议兼容、旧数据库迁移与旧界面接缝。那不是轻量化，
只是把历史复杂度藏起来。

## 两个仓库的职责

| 仓库 | 定位 | 允许的改动 |
|---|---|---|
| `AA4C-ORG/AA4C` | 第二代唯一主仓库 | 新设计、新代码、新发布 |
| 第一代仓库（建议转入 `AA4C-ORG` 后归档）| 第一代历史与安装包 | 只做严重安全修复和归档说明，不再加功能 |

两个版本不共享协议、数据目录或版本号承诺。第二代开始发布前，第一代 README 必须在首屏说明「旧版、已停止功能开发、
与新版不互通」。仓库转移、改名、创建 GitHub 仓库和推送都由维护者亲自完成，不由 agent 自动执行。

## 第二代不可突破的五个接缝

1. **产品接缝**：核心只包含身份、发现、连接、发送、共享空间、常开设备；下载器与 AI 永久退出。
2. **调用接缝**：所有用户行为进入同一个命令注册表。界面、CLI、MCP、测试与插件不另开业务入口。
3. **安全接缝**：调用必须带 `CallerContext`；能力级别、文件根目录、人类确认和运行限额在分发器统一检查。
4. **平台接缝**：业务逻辑在 Rust 引擎；桌面 Rust UI 与原生手机薄壳只画界面、接系统能力。
5. **扩展接缝**：第三方代码只以受限 WebAssembly 运行，只返回意图，不取得宿主文件系统、网络或信任能力。

这五个接缝同时也是最高层测试接缝。只测某个 UI 按钮或内部 service 不足以证明一个功能完成。

## 可以移植什么

移植按「行为 + 回归测试」进行，不按文件或 crate 搬家。

**允许候选**：路径净化、BLAKE3 流式校验、续传边界、QUIC 收尾语义、双栈监听、连接失败分类、
取消与关停语义。这些都必须先写成第二代的外部行为测试，再移植能让测试通过的最小纯 Rust 逻辑。

**不搬**：Tauri/Vue 外壳、SQLite schema 与迁移、第一代 `Core`/Service 编排、下载/归档/AI crate、
TCP 与 QUIC 双路径、旧协议类型、旧插件 trait、任何生成的 Android/Tauri 目录。

移植第一代代码前还要确认许可证与贡献者授权；无法确认时按规格重写，不复制实现。

## 实施顺序

### 0. 先把未知变成实验

M0 只做能推翻设计的最小实验：原始公钥 QUIC、UniFFI Android、egui/Slint 桌面原型、默认信标隐私，
以及首份依赖清单；近场平台能力矩阵放到 M3 开工前。完整清单以[路线图](roadmap.md)为准。实验结果回写 ADR；失败时改设计，不把实验代码偷偷长成产品代码。

### 1. 先交付纵向最小切片

第一条产品切片只有：`nearby.list` → `send.files` → 对端 `inbox.accept` → 完成事件。
桌面版与 CLI 都走命令注册表，测试也只从该接缝进入。没有命令、事件、错误码与对抗性参数测试的 UI 不合入。

### 2. 每个里程碑都守预算

每次合入记录：新增的直接依赖、唯一传递依赖数、二进制大小、冷启动时间和新增的非 Rust 代码。
依赖预算不是最终清理任务，而是每个 PR 的门禁。具体阈值见[分层与 crate](architecture/crates.md)。

### 3. 先证明真实场景，再扩大范围

每个里程碑的结束条件是「真人在真设备完成场景」加自动化回归，不是 crate、页面或命令数量。
M1 没有稳定完成两台真机附近互传前，不开始空间同步；M4 没有连接阶梯数据前，不承诺远程必达。

## GitHub 组织与 aa4c.com

建议最终布局：

```text
AA4C-ORG/AA4C          主仓库
AA4C-ORG/aa4c.com      官网静态文件（也可在主仓库的 site/，M9 决定）
```

`aa4c.com` 只提供网站、下载、文档与链接落地页，不承担账号、发现、中转或文件存储。
DNS、GitHub Pages、自定义域名验证、仓库转移与 Release 迁移都需要维护者账号操作，实施时按独立清单逐项确认，
不要把令牌写进仓库或交给 agent。

## 何时可以开始写产品代码

以下条件同时满足才开始 M0 的实验与仓库骨架：

- 本书、术语表与 ADR 之间没有已知矛盾；
- 命令描述与 `CallerContext` 的最小 schema 已定；
- CI 能检查分层、依赖预算、文档链接与格式；
- 每个 M0 实验都有一个明确问题、成功条件和删除条件。

许可证必须在移植或发布第一行产品代码前决定；存储选型与旧仓库处理在 M0 结束前决定，
没有结论就不进入 M1 的产品切片。

路线图按用户场景安排后续交付，见[路线图](roadmap.md)。
