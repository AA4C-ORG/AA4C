# 待细化的问题

设计里还没想清楚、需要讨论后再定的问题，按重要性排序。每条写明：为什么重要、有哪些选项、目前倾向。
讨论有结论后：改对应章节；难回头的写 ADR；然后从本页删掉。

---

## A. 身份与信任（最需要讨论）

### 1. 设备失窃：拿到我设备的人等于拿到了「我」

**为什么重要**：个人私钥存在我的每台设备上。手机被偷、且锁屏被绕过时，对方能以我的身份给联系人发东西、签发新设备，
甚至**抢在我之前吊销我的其他设备**，把我锁在自己的身份之外。

**选项**：
- **A. 单层（最简单）**：个人私钥在每台设备上，丢了就从别的设备吊销。抢先吊销的风险靠「吊销需要用户在设备上确认生物识别/锁屏密码」降低。
- **B. 两层**：**身份根**（由恢复码推导，平时不在任何设备上，只用于签发/轮换下一层和紧急吊销）+ **个人签名密钥**（在设备上，签设备证书）。
  丢了设备：用恢复码轮换签名密钥，联系人只认身份根签过的新签名密钥。类似 Matrix 的交叉签名、Keybase 的设备模型。
- **C. 只在「主设备」上**：个人私钥只放在用户指定的一两台设备（如手机 + 一台电脑），其他设备只有设备证书，不能签新设备。

**目前倾向**：v1 用 A + 「吊销与签发新设备都要求系统级用户验证（Face ID / 指纹 / 锁屏密码）」，数据格式上为 B 预留升级路径
（证书里写明签发者类型）。需要评估：A 的残余风险普通用户能否接受；B 对「没存恢复码的大多数人」是否形同虚设。

### 2. 恢复码

**为什么重要**：没有账号就没有找回。所有设备都丢了 = 身份没了，联系人要重新加，空间要重新被邀请。

**待定**：是否在首次设置时强制提醒保存；格式（中文词表助记词？数字分组？可打印的二维码？）；是否支持「交给一位信任的联系人保管一半」这类社交恢复。

### 3. 我的设备之间如何同步「个人状态」

联系人列表、空间、吊销、设置要在我的设备之间保持一致，而设备经常离线、可能同时修改。

**选项**：每条记录「最后写入者胜」+ 逻辑时钟（简单，偶有覆盖）；签名的追加日志 + 合并规则（可审计，复杂）；CRDT（自动合并，引入依赖）。

**目前倾向**：联系人与设置用「最后写入者胜」；吊销与空间成员用签名链（只增不改，天然可合并）。

### 4. 签名内容的序列化格式

设备证书、吊销、空间成员链需要「对同一内容，所有实现算出同一串字节」才能验签。

**选项**：JSON 规范化（RFC 8785 JCS）；固定字段顺序的简单二进制布局 + 域分隔前缀。**目前倾向**：二进制布局（实现小、无歧义），
对外展示仍用 JSON。

### 5. 新设备不在同一网络时能否加入「我」

例：在单位新装了一台电脑，手机在家。扫码要求两台设备能直接连上。

**选项**：经中转站建立通道 + 更强的核对（例如输入更长的口令）；或者规定必须当面（同一网络）加入。**目前倾向**：当面加入是默认路径；
只有在有可用中转站时才提供远程加入，并且必须比对核对码，不能只凭口令。

### 6. 邀请链接是否强制核对码

链接经微信等渠道传递，可能被他人截获并抢先使用。强制双方电话互读核对码最安全，但大多数人不会做。

**目前倾向**：默认不强制，但 A 确认时清楚显示「这个人的名字、来自哪里」与核对码，并提示「不确定就打个电话对一下」；
邀请默认一次性、7 天过期。

## B. 发现与连接

### 7. 默认信标的帧格式与扩展上限

[ADR 0015](../../docs/adr/0015-private-nearby-discovery.md) 已提议使用联系人发现密钥，解决稳定设备公钥暴露身份的问题。
M0 仍要决定：AEAD、轮换周期、填充档位、每包条目上限、联系人多时的分批策略、最坏发现延迟，以及删除联系人后的密钥擦除。

**通过标准**：被动抓包不能凭信标载荷认出设备主人，也不能跨网络、跨轮换周期关联设备（同一网络内的 IP/MAC 关联不在此列）；条目数只暴露填充档位；重放旧包无效；畸形包的解析时间和内存有界；100 个联系人时仍满足确定的发现延迟预算。

### 8. 没有中转站时，远程设备怎么找到对方

只靠「上次已知地址」，地址一变就失联（见[连接阶梯](network/ladder.md)）。

已决定不让联系人转告第三人的地址，避免泄露关系图；只有我的设备互相同步地址。仍待定：地址缓存保留多久、失败几次后标为失效，
以及何时在界面上主动建议用户设置常开中转站。

### 9. 社交中转的边界

替联系人转发流量会占用我家的带宽；转发的虽然是密文，但「我的网络替别人转发过数据」是否带来法律或运营商层面的风险？

**待定**：默认限额是多少；是否只允许「空间成员」而不允许「任意联系人」；界面如何说明风险。

### 10. 封 UDP 的网络

只用 QUIC 意味着在封 UDP 的网络（部分公司、酒店、校园网）里只能经中转站，而中转站本身也走 UDP。

**待定**：中转站是否在 v1 就提供 TCP 回退通道（增加一条代码路径，违背 ADR 0004 的初衷）；或 v1 先如实提示「这个网络不支持」。

## C. 共享空间与同步

### 11. 多个所有者同时修改成员表

两个所有者在离线时各自加人、删人，成员链分叉。**目前倾向**：v1 每个空间只允许一个所有者修改成员表（其他人可以「提议」），v2 再考虑多所有者合并规则。

### 12. 共享文件夹的同步语义

- 每台设备存全部，还是只存元数据、按需取回（第一代的做法）？手机存储有限。
- **删除是否同步**：一个成员误删，所有人都丢了？**目前倾向**：删除同步，但进各设备的「AA4C 回收站」保留 30 天。
- 冲突：两人同时改同一个文件，保留两份（「文件名（张三的版本）」），不自动合并。
- 「只读」成员本地改了文件怎么办：不上传，界面提示。

### 13. 发给「张三」时发到他的哪台设备

张三有手机、电脑、平板，可能同时在线。**选项**：发到他设的「首选设备」；发到所有在线设备由他任一台接收；问发送方选哪台。
**目前倾向**：默认发到他的首选设备（他自己设置），不在线则发给任一在线设备；高级选项可指定设备。

## D. 外壳

### 14. 桌面界面用 egui 还是 Slint

egui：photocraft 证明了能做大型应用；依赖可控；观感偏「工具」。Slint：更像消费级应用，自带 Android 支持；**许可证**为 GPLv3 / 免版税许可（要求在「关于」页署名）/ 商业许可三选一，
需确认与本项目许可证的搭配。M0 做两个原型对比后定。

### 15. iOS 后台接收

iOS 不允许 App 在后台长期监听。「手机放口袋里，电脑发过来的文件自动收下」在 iOS 上无法完全可靠。

**选项**：收到前台通知才接收（需要推送，而推送需要服务器——违背原则）；只在 App 打开时接收，由发送方排队等待并自动重试；
借助「本地网络 + 短时后台任务」尽量延长。**目前倾向**：发送方排队自动重试 + iOS 上明确提示「打开 AA4C 才能收」。

### 16. 扫码收发页的明文 HTTP

同一本地 IP 链路上有能力抓包的人可能截获内容。**选项**：接受并提示（当前）；页面用少量 JavaScript 在浏览器里解密（口令放在 `#` 后不经网络）——
安全得多，但违背「收发页不用 JavaScript」。**需要权衡**：是否为这一页破例允许极少量、可审计的 JavaScript。

## E. 分发与工程

### 17. 国内应用商店上架

中国大陆的安卓应用商店与 App Store（中国区）要求 App 备案；点对点文件传输类应用的审核尺度不明。**需要调研**：备案主体、所需材料、
是否影响「无服务器」的设计说明；不上架时的分发方式（官网直装 APK、F-Droid、GitHub Releases）。

### 18. 许可证

第一代是 Apache-2.0。**倾向**：第二代用 Rust 生态惯例的 `MIT OR Apache-2.0`。若移植第一代代码，需确认第一代的贡献者同意。

### 19. 第一代仓库如何处理

**倾向**：先把 `HuoTaoCN/AA4C` 改名为 `aa4c-legacy`，再转移到 `AA4C-ORG` 并归档；这样不与组织下的新 `aa4c` 同名，
并保留历史、star、Release 与旧地址跳转。转移要组织方接受，执行前还要检查 fork、Pages、Actions secrets 与包发布权限。

### 20. redb 还是 fjall

两者都是纯 Rust 嵌入式存储。M0 比较依赖数、稳定性、崩溃一致性、数据格式升级的难易后定（[ADR 0006](../../docs/adr/0006-redb-not-sqlite.md)）。

## F. 远程访问

### 21. 远程访问能否开放给联系人（远程协助）

帮爸妈处理电脑问题是远程桌面最常见的用途之一，但它跨出了「我的设备」：爸妈要把远程桌面服务临时开放给我这个联系人
（[远程访问](network/remote-access.md)）。

**选项**：按联系人、按服务长期开放；只允许被协助的一方每次在场开启、限时自动关闭（像「所有人」模式）；完全不做，交给 SubnetDesk 自己的认证。

**目前倾向**：v1.0 只做我的设备；远程协助另写 ADR，要求被协助方每次在场开启、限时、可随时断开，开启是 trust 级操作。
