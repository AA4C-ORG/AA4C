# 近场交付：安装可选，路径可选

人在同一个现场时，接收方可以安装 AA4C，也可以不安装直接收文件；发送方不应为了换一种无线方式重新选一遍文件。
跨网络的远程接收则必须安装 AA4C。这个产品边界由
[ADR 0016](../../../docs/adr/0016-no-remote-browser-share-in-v1.md) 确定。

## 三条交付路径

| 界面选项 | 接收方要求 | 底层路径 | 安全语义 | 适合 |
|---|---|---|---|---|
| **用 AA4C 接收** | 已安装 AA4C | 现有 QUIC 传输；可运行在局域网、Wi-Fi Direct 等可用链路上 | AA4C 设备认证 + 端到端加密 | 私密文件、续传、大文件 |
| **扫码直接收** | 浏览器即可 | 同一局域网，或 Wi-Fi Direct / 临时热点建立的本地 IP 链路；发送方提供 Web drop | 随机口令；当前为明文 HTTP | 临时给身边的人，不想安装 |
| **用系统直接发送** | 取决于接收设备 | 操作系统的分享面板（AirDrop、Quick Share、蓝牙发送等）| 系统自己的配对、确认与加密语义 | 当前两台设备恰好都支持 |

三条路径共享文件选择、大小检查、文件名净化和结果事件，不共享不存在的安全保证。界面默认推荐当前最快且安全的可用路径，
但必须有「换一种方式」；每个选项旁边写清接收方要做什么。用户选「用 AA4C 接收」时，不能静默降级到明文网页或系统直传。

## 无线路径怎样接进来

无线技术分成两类，避免为每一种技术重写文件传输：

1. **本地 IP 链路**：同一局域网、Wi-Fi Direct、Wi-Fi Aware、临时热点等只负责让两端获得可互访的地址。
   链路建好后，双方已安装就复用 AA4C QUIC；接收方没安装就复用扫码收发 HTTP。Wi-Fi Direct 不是第四套文件协议。
2. **系统文件交付**：通常就是调起系统分享面板，由系统完成设备选择与发送。平台薄壳把能力报告给引擎，并按引擎产生的计划调用系统。
   AA4C 只记录「已交给系统 / 用户取消 / 系统报告失败」，不假装能看到系统没有返回的逐字节进度。

Android 的 Wi-Fi Direct 可以在没有网络或热点时建立 P2P 组，并在组内使用标准 socket；经典蓝牙也公开 RFCOMM 数据通道。
Apple 平台的 Network framework 可按系统和硬件能力启用点对点 Wi-Fi，新平台还可能提供 Wi-Fi Aware。实现时以平台运行时探测为准，
不以设备名称或系统版本字符串猜测：

- [Android Wi-Fi Direct](https://developer.android.com/develop/connectivity/wifi/wifi-direct)
- [Android Bluetooth](https://developer.android.com/develop/connectivity/bluetooth)
- [Apple 点对点网络 API 选择](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)

**蓝牙低功耗不是 v1 大文件通道**；它可以用于发现或引导，但没有真机吞吐与稳定性数据前不进入批量文件完成标准。
**红外 v1 不做**：主流桌面与手机系统都已不提供红外文件传输接口，不给用户一个注定失败的按钮。

## 命令与平台接缝

- `proximity.routes`：返回当前可用路径、接收方要求、风险说明、是否需要人操作和不支持原因；推荐只出现在这里。
  结果可以为空，但不能把未知写成可用。
- `proximity.send`：接收文件项与明确的路径 id（AA4C 直连或扫码收发），不接受「自动」。它复用 `send.files` 或 `webdrop.start`，
  不另写一套传输业务逻辑。
- `proximity.handoff`：交给系统分享面板或平台近场发送能力，命令描述静态标记 `human_step = true`：系统设备选择、配对和确认
  由现场的人完成。MCP 可以读取可用路径，但不能替人点击系统确认。
- 平台薄壳只提供 `capabilities / prepare / cancel` 这类窄适配；大小预算、路径授权、文件净化、审计事件和错误分类仍在 Rust 引擎。

这是一条真实的平台接缝：至少有本地 IP 与系统交付两类实现。它不新增一个「万能无线」crate；Android / iOS 适配留在各自薄壳，
桌面系统能力留在桌面外壳，公共选择策略和状态机留在 Rust。

## 现场流程

1. 发送方选文件，打开「当面发送」。
2. AA4C 调 `proximity.routes`，显示可用路径；不可用路径只在「为什么没有」里解释，不占主界面。
3. 选「用 AA4C 接收」时，两端沿正常的附近发现与发送流程；选「扫码直接收」时显示二维码；没有共同局域网时，
   平台若能建立临时本地网络，先给出加入网络的系统步骤，再显示收件二维码。
4. 选「用系统直接发送」时，AA4C 打开系统选择器；用户选定真实设备并完成系统确认。
5. AA4C 只陈述它能证明的结果：引擎传输可报告校验完成；平台交付若只报告「已提交」，界面就不能写「对方已收到」。

## M3 开工前必须验证

近场能力决定近场路径怎么做，推翻不了核心设计，所以不放进 M0。

- Android 真机：Wi-Fi Direct 或临时热点建立本地 IP 后，已安装的对端能走 QUIC；未安装的对端能按系统允许的步骤打开扫码收发页。
- Apple 真机：列出各目标系统版本能用的点对点网络 API、权限和前后台限制；iOS 实现阶段不得沿用已废弃 API 作为新基线。
- Windows、macOS、Linux、Android、iOS 逐一产出能力矩阵：本地 IP、建网、经典蓝牙、系统文件交付；「系统没有公开接口」也是有效结论。
- 用假平台适配器测试能力在运行中消失、用户取消、权限拒绝、建立链路超时和只报告「已提交」的状态，不允许 panic 或误报送达。
- 记录新增依赖与权限。平台 API 能完成时不引入跨平台无线框架，也不为一个条件性功能突破依赖预算。
