# 远程访问：SSH 与远程桌面

> 决定见 [ADR 0017](../../../docs/adr/0017-remote-access-by-service-forwarding.md)。属于 v1.0 的 P1 范围，排在路线图 M6。

[场景 6](../product/users.md) 里的人想要的不只是取文件：在单位 SSH 到家里的 NAS，在外面远程控制家里的电脑。今天的做法是 Tailscale（要账号），
或 SubnetDesk 这类局域网远程桌面再加一层 VPN。AA4C 已经有它们缺的两样东西：不靠账号的「我的设备」身份，和能穿过 NAT 的连接阶梯。
远程访问只在这之上加一层很薄的**服务转发**。

## 做什么、不做什么

| 做 | 不做 |
|---|---|
| 把我一台设备上的本机 TCP 服务（SSH、远程桌面、NAS 管理页）接到我另一台设备的本机端口 | 虚拟网卡、虚拟 IP、子网路由、出口节点、自动域名一类的完整 VPN |
| SSH 用系统自带的 `ssh`，认证仍由 sshd 负责 | 自己实现 SSH，或替代 SSH 的认证 |
| 远程桌面交给 SubnetDesk 或系统自带的远程桌面 | 在引擎里做截屏、输入注入、音视频编解码 |
| 只在我的设备之间 | 对联系人开放（远程协助，见[待细化的问题](../open-questions.md)）|
| TCP | UDP |

不做成插件、不在引擎里做远程桌面、不做虚拟网卡的理由见 ADR 0017。

## 服务与端口转发

- **服务**：一台设备开放给「我的其他设备」的本机地址，例如 `ssh → 127.0.0.1:22`、`远程桌面 → 127.0.0.1:21118`。
  默认一个都没有。开放服务是 `trust` 级操作，界面写明「我的其他设备从此可以连到这台机器的 SSH」。
  服务表经我的设备之间的 `peers.sync` 同步，发起端因此知道每台设备开放了什么。
- 目标地址默认只能是回环地址。要开放局域网里的其他地址（如路由器管理页 `192.168.1.1:80`），必须逐个写明 IP 与端口，不能写网段，
  免得整台设备变成通向家里局域网的开放代理。
- **端口转发**：发起设备开一个只监听 `127.0.0.1` 的本机端口，每个进来的 TCP 连接对应一条到目标设备的 QUIC 双向流。
  不监听 `0.0.0.0`，同一个咖啡馆网络里的其他人用不了我的转发。

转发不需要新的连接层：它只是同一条端到端 QUIC 连接里的另一种流，沿用[连接阶梯](ladder.md)、[中转站](relay.md)与设备认证，也不新增依赖。
经中转站时远程桌面会明显变慢，界面照常显示当前档位。

能连上的范围与连接阶梯完全相同：直连可达，或有可用的自建中转站时才行；封 UDP 的网络目前连不上
（[待细化的问题](../open-questions.md)第 10 条）。连不上时按[连接阶梯](ladder.md)「连不上时」一节说明原因，不承诺「任何网络都能连」。

## 线路

在[线路协议](wire.md)之上增加一条控制消息：

| 消息 | 方向 | 用途 |
|---|---|---|
| `tunnel.open` | 发起 → 目标 | 指明服务名；目标确认对方是我的设备、服务存在后回 `tunnel.ok`，之后这条流上是双向裸字节 |

目标设备只按自己保存的服务表连本机地址，不接受发起方给出的任意地址。一端关闭写端时半关闭另一端，与 `send.done` 的收尾规则一致。

## SSH

不开本机端口也能用：`aa4c connect <设备> <服务>` 把标准输入输出接到目标服务，正好作为 ssh 的 `ProxyCommand`：

```text
# ~/.ssh/config
Host nas
  ProxyCommand aa4c connect nas ssh
```

之后在单位或外面，只要连接阶梯能连上那台 NAS，`ssh nas` 就能用。`aa4c ssh-config` 把我所有开放了 SSH 的设备打印成这样的配置段，由人自己决定是否写进文件。
主机密钥校验与登录认证仍由 SSH 负责，AA4C 只是运输。

## 远程桌面

AA4C 不画远程桌面，只把连接送到。

| 目标设备上的远程桌面 | 开放的服务 |
|---|---|
| SubnetDesk（Windows、macOS、Linux、Android）| `127.0.0.1:21118`（SubnetDesk 默认端口）|
| Windows 自带远程桌面（专业版及以上）| `127.0.0.1:3389` |
| macOS 屏幕共享 | `127.0.0.1:5900` |

发起端在「我的设备」页点「远程桌面」：AA4C 打开端口转发，再把 `127.0.0.1:<本机端口>` 交给 SubnetDesk 或系统客户端。
SubnetDesk 有 `--connect` 参数，M6 要验证它能直接接受这个地址；不支持命令行传地址的客户端，就显示地址让人粘贴。

和 SubnetDesk 配合时的建议设置：来源网段白名单只留 `127.0.0.1/32`，关掉它自己的局域网广播，让所有远程桌面连接都先经过 AA4C 的设备认证；
SubnetDesk 的用户名密码与设备指纹照常保留，作为第二道门。

集成是进程之间的约定，不是代码合并：SubnetDesk 只通过 `aa4c commands --json` 与 `aa4c run` 读取我的设备、打开端口转发；
AA4C 不链接 SubnetDesk 的任何代码，两边的许可证互不影响。SubnetDesk 一侧的改动放在 `AA4C-ORG/SubnetDesk`，不进本仓库。

## 安全

- 只有「我的设备」能用我开放的服务；设备被吊销后，它的端口转发立即断开，也不能再开。
- 开放服务是 `trust`；打开端口转发是 `act`，但 MCP 默认不暴露，需启动时显式 `--allow-tunnel`。
- 丢失的手机在被吊销前可以打开到 NAS 的 SSH 转发，所以 AA4C 不替代 SSH 与远程桌面自己的认证：转发只解决「连得上」。
- 每个服务有并发与带宽上限；经中转站的转发同样受中转站限额约束。
- 每次转发的时间、发起设备、服务与字节数留在目标设备上，可在「我的设备」页查看。

## 命令

能力级别见[命令一览](../architecture/commands.md)的 `services` 与 `tunnel` 两行。命令行：`aa4c services [list|publish|unpublish]`、`aa4c tunnel <设备> <服务> [--local-port <端口>]`、
`aa4c connect <设备> <服务>`（标准输入输出，给 ssh 用）、`aa4c ssh-config`。

## 平台

- 桌面版与 `aa4c`：既能作目标，也能作发起端。
- Android：同上；作发起端时由 AA4C 前台服务持有本机端口，手机上的 SSH 客户端连 `127.0.0.1`。
- iOS：只在前台时作发起端；不作目标（后台不能常驻监听，见[待细化的问题](../open-questions.md)第 15 条）。

## M6 完成标准

- 在单位网络用 `ssh nas` 登录家里的 NAS，公网直连、打洞、经中转站三种档位各跑通一次；
- 在外面用 SubnetDesk 控制家里的 Windows 电脑，SubnetDesk 只接受 `127.0.0.1`；
- 被吊销设备的转发立即断开；未开放的服务、局域网其他地址、伪造的服务名全部被拒；
- 测试台覆盖半关闭、取消、超限与中转站重启。
